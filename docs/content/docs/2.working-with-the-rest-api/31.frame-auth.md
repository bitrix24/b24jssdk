## Getters
### isAdmin
```ts-type
get isAdmin(): boolean
```

Returns `true` if the current user has admin rights, otherwise `false`.

### getAuthData
```ts-type
getAuthData(): false | AuthData
```

Returns authentication data [`AuthData`{lang="ts-type"}](https://github.com/bitrix24/b24jssdk/blob/main/packages/jssdk/src/types/auth.ts) if it has not expired. If expired, returns `false`.

### refreshAuth
```ts-type
async refreshAuth(): Promise<AuthData>
```

Refreshes authentication data through the parent window and returns the updated data [`AuthData`{lang="ts-type"}](https://github.com/bitrix24/b24jssdk/blob/main/packages/jssdk/src/types/auth.ts).

::note
Concurrent calls are **coalesced**: while a refresh is in flight, every further call gets that same promise back rather than sending a second `refreshAuth` message to the parent window. This matters because a `B24Frame` runs two transports (`restApi:v2` and `restApi:v3`) over one `AuthManager`, and because refreshing too often is what Bitrix warns can get an application blocked automatically. A refresh started *after* the previous one settled is a real refresh — the coalescing window is only the time one is actually in flight.
::

::tip
You rarely need to call this yourself. The SDK refreshes an **already expired** token before a request — a valid one is used as is, so a call does not cost a refresh — and refreshes again if the portal answers `401`. If your app reads the token with `getAuthData()` and uses it outside the SDK, prefer [`keepAuthFresh`](/docs/working-with-the-rest-api/frame-initialize-b24-frame/#keeping-the-token-alive) over your own timer.
::
