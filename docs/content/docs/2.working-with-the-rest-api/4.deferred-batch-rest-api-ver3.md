## Overview

`$b24.actions.v3.deferredBatch` wraps the portal's `rest.deferredbatch.*`
methods. A deferred batch is a **background job**:

1. `rest.deferredbatch.add` takes **all** commands in one call — thousands of
   them, far past the 50 of a synchronous [`batch`](/docs/working-with-the-rest-api/batch-rest-api-ver3/).
   Measured: 5000 commands in one job.
2. The portal runs them in the background. The job's status goes
   `pending` → `processing` → `done` (or `error`).
3. The results are stored as a gzip-compressed JSON file. The SDK downloads it
   and decodes it into rows — one row per command, in command order.

Compared with [`batchByChunk`](/docs/working-with-the-rest-api/batch-by-chunk-rest-api-ver3/),
which sends one request per 50 commands and spends your operating-time budget
on each, a deferred batch is one request to start and a few cheap status checks.

::warning
Deferred batches depend on the portal's **plan**. On a plan without them every
call answers `FEATURE_NOT_AVAILABLE_ON_CURRENT_PLAN`. The webhook or
application also needs the `rest` scope.
::

There are two ways to use it:

| You want to… | Use |
| --- | --- |
| Run the commands and get the rows, with a progress callback | [`make()`](#method-signature) |
| Start a job now and collect it later — another request, a queue worker, your own UI polling | [the single steps](#step-by-step) |

## Method Signature

```ts-type
make<T = unknown>(options: ActionDeferredBatchV3): Promise<Result<T[]>>

add(options: ActionDeferredBatchAddV3): Promise<Result<DeferredBatchJob>>
get(id: number): Promise<Result<DeferredBatchJob>>
waitFor(id: number, options?: ActionDeferredBatchWaitV3): Promise<Result<DeferredBatchJob>>
download<T = unknown>(id: number): Promise<Result<T[]>>
delete(id: number): Promise<Result<boolean>>
list(): Promise<Result<DeferredBatchJob[]>>
getDownloadUrl(id: number): Promise<Result<string>>
decode(bytes: ArrayBuffer | Uint8Array): Promise<unknown[]>
```

### All in one: `make()`

```ts
// const $b24 = ...
import type { BatchCommandsArrayUniversal, DeferredBatchJob } from '@bitrix24/b24jssdk'

interface TaskRow { item?: { id: number, title: string } }

const calls: BatchCommandsArrayUniversal = Array.from({ length: 2000 }, (_, i) => [
  'tasks.task.get',
  { id: i + 1, select: ['id', 'title'] }
])

const response = await $b24.actions.v3.deferredBatch.make<TaskRow>({
  calls,
  // Called on every status change: pending → processing → done.
  onStatus: (job: DeferredBatchJob) => console.log(`job #${job.id}: ${job.status}`)
})

if (!response.isSuccess) {
  throw new Error(response.getErrorMessages().join('; '))
}

const rows = response.getData()! // one row per command, in order
const titles = rows.flatMap(row => row.item ? [row.item.title] : [])
console.log(`${titles.length} of ${rows.length} tasks found`)
```

`make()` adds the job, waits for it, downloads and decodes the result file, and
deletes the job. What the portal answers never makes it throw: check
`isSuccess`. It throws only for malformed `calls`, before anything is sent.

#### Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `calls` | `DeferredBatchCalls`{lang="ts-type"} | — | The commands: `[['method', params], …]`, `[{ method, params }, …]`, or both mixed. Named commands are not supported — the result is an array. |
| `onStatus` | `(job: DeferredBatchJob) => void`{lang="ts-type"} | — | Called when the status changes, the first status included. An exception in it is logged and ignored. |
| `pollInterval` | `number`{lang="ts-type"} | `2000` | Milliseconds between status checks. At least `250`. |
| `timeout` | `number`{lang="ts-type"} | `600000` | Milliseconds to wait for `done` / `error`. |
| `signal` | `AbortSignal`{lang="ts-type"} | — | Stops waiting. |
| `deleteAfter` | `boolean`{lang="ts-type"} | `true` | Delete the job and its file after reading. |
| `idempotencyKey` | `string`{lang="ts-type"} | — | Sent with `add`: a retried `make()` with the same key and the same commands reuses the job instead of starting a second one. See [Idempotency-Key](/docs/working-with-the-rest-api/call-rest-api-ver3/#idempotency-key). |
| `requestId` | `string`{lang="ts-type"} | — | Sent as `bx24_request_id` with `add`. |

## Examples

### Progress in a UI, and cancelling

```ts
// const $b24 = ...
declare const calls: [string, Record<string, unknown>][]
declare function showStatus(text: string): void

const controller = new AbortController()
// e.g. wired to a "Cancel" button: cancelButton.onclick = () => controller.abort()

const response = await $b24.actions.v3.deferredBatch.make({
  calls,
  pollInterval: 3_000,
  timeout: 30 * 60_000,
  signal: controller.signal,
  onStatus: job => showStatus(job.status === 'done' ? 'Downloading results…' : `Status: ${job.status}`)
})

if (!response.isSuccess) {
  // JSSDK_DEFERRED_BATCH_ABORTED, _TIMEOUT or _FAILED — see "Errors" below.
  showStatus(response.getErrorMessages().join('; '))
}
```

Aborting or timing out stops **waiting**, not the job: it keeps running on the
portal, and can be collected later with the steps below.

### Step by step

Each step is one method and returns a `Result`:

| Method | Portal method | Returns |
| --- | --- | --- |
| `add({ calls, idempotencyKey?, requestId? })` | `rest.deferredbatch.add` | `Result<DeferredBatchJob>`{lang="ts-type"} — the new job, usually `pending` |
| `get(id)` | `rest.deferredbatch.get` | `Result<DeferredBatchJob>`{lang="ts-type"} |
| `waitFor(id, { pollInterval?, timeout?, signal?, onStatus? })` | `rest.deferredbatch.get`, repeated | `Result<DeferredBatchJob>`{lang="ts-type"} — the job in its final state |
| `download<T>(id)` | `rest.deferredbatch.downloadresult` + the file | `Result<T[]>`{lang="ts-type"} — the decoded rows |
| `delete(id)` | `rest.deferredbatch.delete` | `Result<boolean>`{lang="ts-type"} |
| `list()` | `rest.deferredbatch.list` | `Result<DeferredBatchJob[]>`{lang="ts-type"} |
| `getDownloadUrl(id)` | `rest.deferredbatch.downloadresult` | `Result<string>`{lang="ts-type"} — the file link (a credential, see below) |
| `decode(bytes)` | — | `Promise<unknown[]>`{lang="ts-type"} — gunzip + JSON of file bytes |

#### Start now, collect later

```ts
// const $b24 = ...
declare const calls: [string, Record<string, unknown>][]
declare function saveJobId(id: number): Promise<void>
declare function loadJobId(): Promise<number>

// Request 1: start the job and remember its id.
const added = await $b24.actions.v3.deferredBatch.add({ calls })
if (!added.isSuccess) {
  throw new Error(added.getErrorMessages().join('; '))
}
await saveJobId(added.getData()!.id)

// Request 2, later: is it ready?
const jobId = await loadJobId()
const job = (await $b24.actions.v3.deferredBatch.get(jobId)).getData()

if (job?.status === 'done') {
  const rows = await $b24.actions.v3.deferredBatch.download(jobId)
  console.log(`${rows.getData()?.length ?? 0} rows`)
  await $b24.actions.v3.deferredBatch.delete(jobId)
} else if (job?.status === 'error') {
  console.error(job.errorMessage)
}
```

#### The job object

```ts-type
interface DeferredBatchJob {
  id: number
  status: 'pending' | 'processing' | 'done' | 'error'
  commands?: Array<{ method: string, query: Record<string, unknown> }>
  createdAt?: string
  updatedAt?: string
  resultFileId?: number | null // set once `done`
  errorMessage?: string | null // set when `error`
}
```

## The result rows

A row is what that command returned, in command order — the same shape as one
entry of a synchronous v3 `batch` result: `{ item }` for a `get`, `{ items }` for
a `list`, and so on. The row carries no `time` block.

`download()` / `make()` decode the file for you. If you downloaded it some other
way, `decode()` does the same: it gunzips the bytes (the file is
`application/gzip`) and parses the JSON array. Bytes already inflated — a proxy
that decompressed them — are parsed as they are. Decoding uses the standard
`DecompressionStream`, available in Node.js 18+ and every current browser.

## Security: the download link is a credential

`rest.deferredbatch.downloadresult` answers with an absolute URL that carries
the caller's credential — the webhook secret in the path, or an access token.
The SDK downloads it itself, never logs it, never puts it in an error, and does
not follow redirects with it. `getDownloadUrl()` hands it to you: treat it like
the webhook URL itself. Deleting the job makes the link stop working.

## Error Handling

| Code | When |
| --- | --- |
| `JSSDK_DEFERRED_BATCH_FAILED` | The job ended with status `error`. `waitFor()` returns the job as data, so `getData().errorMessage` has the portal's message. |
| `JSSDK_DEFERRED_BATCH_TIMEOUT` | No final status within `timeout`. The job keeps running. |
| `JSSDK_DEFERRED_BATCH_ABORTED` | `signal` was aborted. The job keeps running. |
| `JSSDK_DEFERRED_BATCH_DOWNLOAD_FAILED` | The result file could not be downloaded; the message names the HTTP status. |
| `JSSDK_DEFERRED_BATCH_DECODE_FAILED` | The file is not valid gzip, or not a JSON array. |
| `JSSDK_DEFERRED_BATCH_GZIP_UNSUPPORTED` | The runtime has no `DecompressionStream`. |
| `JSSDK_DEFERRED_BATCH_EMPTY` | `calls` is empty — thrown, before anything is sent. |
| `FEATURE_NOT_AVAILABLE_ON_CURRENT_PLAN` | The portal's plan has no deferred batches. |

## Alternatives and Recommendations

* **Up to 50 commands, result needed right away:** a synchronous
  [`batch`](/docs/working-with-the-rest-api/batch-rest-api-ver3/) is simpler and
  returns in the same request.
* **More than 50, and the plan has no deferred batches:**
  [`batchByChunk`](/docs/working-with-the-rest-api/batch-by-chunk-rest-api-ver3/)
  does the same work as one request per 50 commands.
* **Reading a whole list:** [`fetchList`](/docs/working-with-the-rest-api/fetch-list-rest-api-ver3/)
  or [`fetchTail`](/docs/working-with-the-rest-api/fetch-tail-rest-api-ver3/)
  page through it without building thousands of `get` commands.
* **Writes that must not repeat:** pass `idempotencyKey`, so a retried `add`
  does not start a second job.
* Do not assume the job is all-or-nothing: nothing here undoes commands that
  already ran. Check each row.
